## Show HN draft — not submitted

**Title:** Show HN: SPECTRA — learn radio with a simulated receiver in your browser

**URL:** https://spectra-one.vercel.app/?view=station

**First comment:**

I built SPECTRA to make it easier to try radio before buying hardware or setting
up SDR software. The first task is to find a signal, tune to it, and hear a
voice. A guided lesson introduces the controls, then a short CTF asks you to
survey a different band on your own.

The signals are generated in a Web Worker as complex I/Q samples. They pass
through a TypeScript receiver with filtering and demodulation before reaching
Web Audio. The simulator knows which emitters it placed, so lessons can check
receiver state and challenges have repeatable answers. The repo includes DSP,
decoder, grading, and lesson tests.

There are also harder radio challenges, signal-reference pages, and US ham
exam practice. No account or radio hardware is needed. It simulates signals;
it does not receive nearby radio traffic. Progress stays in your browser.

I'd like feedback on the first few minutes: is it clear what to do next, and
does changing the receiver help explain what you're hearing?

## Radio-community draft — not submitted

**Suggested title:** A browser radio simulator for practicing tuning without an SDR

I'm building SPECTRA, a free browser simulator for practicing receiver controls
and recognizing signals. The first guided task has you tune broadcast FM and
find a voice station; the next challenge asks you to count the stations in a
new simulated band.

It has lessons on modes, filter bandwidth, squelch, repeaters, scanning, and
reading a waterfall. There is also CW practice, radio CTF work, and ham exam
study. Everything you hear is generated by the simulator, so it is a repeatable
practice environment rather than a live radio receiver.

Try the first lesson: https://spectra-one.vercel.app/?view=station

Or look at the signal reference: https://spectra-one.vercel.app/signals/

I'd appreciate feedback on anything confusing or technically misleading.
If reception or audio behaves badly, the browser and device details would
help me reproduce it.

### 1. Add a short AM-versus-FM listening comparison to the signal reference

**Problem:** a newcomer can read modulation descriptions without knowing what
to listen for when choosing a receiver mode.

**Scope:** improve the existing AM and NFM reference descriptions and their
receiver handoffs. Use existing scenes and controls; do not add a new lesson,
signal model, or progression rule.

**Acceptance criteria:**

- Give one concrete listening/receiver task for each modulation in plain language.
- Cite a primary technical reference for any new modulation claim.
- Reuse existing scenario URLs and verify that each opens the intended band.
- Run the build and confirm the generated AM and NFM pages include the guidance.
  Preserve the shared content source instead of editing `dist/`.

### 2. Align Academy section spacing with the shared interface components

**Problem:** Academy's card and section patterns still differ from the receiver
and exam views, as recorded in the backlog.

**Scope:** one Academy view at a time. Reuse existing spacing tokens,
`GroupLabel`, and shared controls; preserve its teaching content and navigation.

**Acceptance criteria:**

- Identify the specific inconsistent spacing or section pattern with a before
  screenshot and the existing component/token it should use.
- Apply the change without creating a second spacing system or unrelated redesign.
- Verify the affected view at a phone-sized and desktop viewport in both themes,
  including longer text and its existing interactive widgets.
- Pass typecheck and build; report any layout checks not performed.

### 3. Audit first-lesson focus and announcements with a screen reader

**Problem:** the walkthrough's focus order, control names, and progress
announcements need a reproducible screen-reader check.

**Scope:** start from Station and complete Tune and listen with a screen
reader and keyboard. Keep changes within this lesson and its challenge
handoff. Global shortcuts already defer to focused controls and dialogs;
do not reopen the fixed Space-key interception as a new issue.

**Acceptance criteria:**

- Record browser/OS, screen reader, and the exact key sequence for start,
  tuning, and navigation.
- Verify visible focus, meaningful control names, and that the coach does not
  trap or hide focus. Record any unreachable control with a minimal reproduction.
- Check that lesson progress and completion are understandable without the
  visual reticle, without repeatedly announcing every receiver update.
- Fix a confirmed gap with native button/input semantics where practical,
  preserving pointer/touch use and avoiding unrelated shortcut changes.
- Verify the affected keyboard path and normal lesson completion; add a
  behavior regression if a state or navigation bug was corrected.
